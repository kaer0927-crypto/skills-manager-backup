# P3 技术可行性评估

> **定位**：基于功能拆解和项目约束，产出支撑内部决策与对客报价的完整技术评估：复杂度、选型、工作量、排期、成本、风险。
> **产出**：`study/02_可行性评估报告.md`（+ docx）

## 前置输入

- `study/01_功能模块拆解.md`（P2 产出，缺失则先走 P2）
- `Memory.md` 的项目约束（预算、工期、团队、部署环境）
- **`op-prompt.md`（公司技术栈约束规范）**：检查项目根目录是否存在。存在 → 读取全文，作为后续所有步骤的硬约束
- `references/estimation-baseline.md`（本技能自带估算基准，Step 3.4/3.6 必读）

## ⛔ 核心规则：禁止技术栈幻觉

> 1. `op-prompt.md` 已明确规定的 → 原样使用，禁止凭"行业惯例"替换
> 2. 其中已禁止的技术 → 不得出现在推荐方案中
> 3. 其中已声明存在的中间件（如 Kafka、Redis、Nacos）→ 必须纳入选型并标注"已有组件，直接复用"
> 4. 部署方案严格按其部署环境约束（K8s / 政务云 / 安全组等）描述，禁止虚构
> 5. 未提及的第三方云服务（OSS、云负载均衡等）→ 除非明确允许，否则不引入
>
> **`op-prompt.md` 不存在时**：选型可参考行业惯例，但报告中必须注明「未读取到公司技术规范，以下为行业通用方案」。

## 执行步骤

### Step 3.1 — 业务复杂度分析

7 维度评估（低/中/中高/高），每个维度给分析说明：

| 维度 | 看什么 |
|------|-------|
| 业务流程 | 链路长度、分支逻辑、异常处理 |
| 表单设计 | 表单数量、子表嵌套、动态行、自动计算 |
| 审批/工作流 | 场景数、节点深度、并行/会签 |
| 算法/计算 | 复杂算法、推荐、匹配 |
| 数据量/性能 | 数据增长、并发、查询复杂度 |
| 集成/对接 | 外部系统数量、协议复杂度 |
| 安全/合规 | 等保、加密、审计留痕 |

给出「综合业务复杂度」结论（这决定 Step 3.4 的复杂度乘数档位）。

### Step 3.2 — 技术选型（强制约束）

选型表每行标注**约束来源**：

| 技术层级 | 推荐方案 | 约束来源 | 成熟度 | 选型理由 |
|---------|---------|---------|:---:|---------|
| 后端框架 / 前端框架 / 数据库 / 缓存 / 消息队列 / 注册配置中心 / 部署方式 / … | | 公司规范 / 已有组件 / 需额外引入 | ★ | |

若 `op-prompt.md` 存在，选型后**必须**输出「约束覆盖检查清单」：逐条列出 op-prompt.md 条目 → 是否已在选型中体现 ✅/❌。

### Step 3.3 — 脚手架/框架加速评估（如推荐使用）

脚手架名称与版本 → 是否兼容技术栈约束（框架版本、JDK 版本）→ 已覆盖功能对照 P2 清单逐项 ✅/❌ → 预估节省人天 → 二开成本与风险。

### Step 3.4 — 工作量估算（必须基于估算基准）

**先读 `references/estimation-baseline.md`**，按其中的三档基准 + 复杂度乘数逐模块估算，禁止无依据拍数字。

开发工作量（按模块，标注每行用了哪档基准）：

| 模块 | 子功能数 | 档位构成（简单/中等/复杂） | 后端人天 | 前端人天 | 合计 | 说明 |
|------|:---:|:---:|:---:|:---:|:---:|------|

公共能力单列（审批引擎、文件管理等，用基准表的公共能力行）。

非开发工作量：按基准表的占比区间推算（需求分析、原型、UI、DB 设计、环境、联调测试、部署、培训、项目管理），并汇总：**总人天 = 开发 ×（1 + 非开发占比）× 复杂度修正系数**。

**交叉校验**（必做）：可用人天 = 团队人数 × 工期周数 × 5 × 0.8，与估算总人天对比。偏差 >20% → 在报告中显式预警并给出裁剪/加人/延期三选项。

### Step 3.5 — 团队配置与排期推演

1. 推荐团队配置（角色/人数/职责/参与周期）
2. 按周排期（文本甘特图：需求设计 → 核心开发 → 联调测试 → 部署验收）
3. 关键里程碑表（里程碑/时间/交付物/客户确认节点）
4. 工期压缩可能性分析（策略/幅度/代价）

### Step 3.6 — 成本估算

人力成本（角色 × 参与天数 × 日均成本，日均成本参考估算基准的人力单价区间，或用用户提供的公司实际数）＋ 其他成本（差旅/工具/服务器）→ 汇总，并做**与预算的匹配度分析**（预算已知时必做）。

### Step 3.7 — 风险识别

Top 5–7 风险表（风险/概率/影响/应对）。以下 3 个标准风险适用时必含：需求频繁变更、预算与工作量不匹配、远程沟通效率低。
若 `op-prompt.md` 存在，追加技术约束风险：政务云网络限制对接风险、国产化数据库兼容性风险、前端框架版本生态限制风险。

### Step 3.8 — 可行性结论

技术 / 性能 / 安全 / 部署 / 扩展 五个维度 ✅/⚠️/❌ + 说明。

### Step 3.9 — 实施建议

功能范围建议（预算紧张时裁什么）· 交付模式建议（瀑布/敏捷/分里程碑）· 运维建议（质保期/年度运维/二期规划）。

### Step 3.10 — 文档输出

`study/02_可行性评估报告.md` → docx 按«格式转换链»。
