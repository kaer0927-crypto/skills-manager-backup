# PRD 质量自检清单

> 在交付 PRD 文档前，逐项检查以下内容。每项通过打 ✅，不通过打 ❌ 并说明原因。

---

## 一、结构完整性

- [ ] 文档元信息表已填写完整（项目名、负责人、日期、版本、状态）
- [ ] 第一部分（需求分析）的 5 个核心模块均已覆盖（背景目标、用户场景、业务流程、信息架构、需求清单）
- [ ] 第二部分（原型说明）的 3 个核心模块均已覆盖（变更说明、公共部分、功能模块）
- [ ] 补充模块（非功能性需求、数据指标）已按项目实际情况决定是否输出
- [ ] 附录部分（术语表、风险与依赖）已按项目实际情况决定是否输出

## 二、需求分析质量

- [ ] 需求背景清晰回答了"为什么做"，不是空泛的套话
- [ ] 需求目标至少从 1 个维度（业务/市场/运营/产品）给出了可衡量的目标
- [ ] 版本节奏和本期边界已明确，"不做"的内容已列出
- [ ] 所有目标用户角色已定义，无遗漏
- [ ] 核心场景有流程图支撑，异常路径已覆盖
- [ ] 整体业务流程图和泳道图均已绘制
- [ ] 信息结构图覆盖了所有一级和二级菜单
- [ ] 需求清单有优先级标注，P0 需求构成最小闭环

## 三、原型说明质量

- [ ] 变更说明在文档顶部，最新变更记录在最上方
- [ ] 公共部分说明不遗漏权限体系和全局状态定义
- [ ] 每个功能模块有模块级流程图
- [ ] 列表页说明包含筛选条件、字段定义、操作按钮
- [ ] 表单页说明包含字段清单表（类型/必填/校验/默认值）
- [ ] 页面交互状态已考虑：加载中、空状态、错误状态
- [ ] 涉及审批/流转的功能已标注状态流转规则

## 四、表述质量

- [ ] 功能说明具体到可执行，不含"灵活"、"优化"等模糊词
- [ ] 无自造缩写或术语——所有术语在术语表中有定义
- [ ] 每条需求的边界清晰——做什么、不做什么写得明确
- [ ] 数字化表达——容量、时长、数量有明确约束值

## 五、协作友好度

- [ ] 研发团队阅读后能直接进入技术方案设计，无需频繁反问产品
- [ ] 设计师阅读后能明确每个页面的信息层级和交互行为
- [ ] 测试人员阅读后能从文档中提取测试用例
- [ ] 文档命名规范：`PRD-[项目名称]-Vx.x.md`
