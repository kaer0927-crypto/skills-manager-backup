# PRD 产品需求文档撰写器

> 作者：liuyz
> 方法论基础：To B 高级产品经理 8 年实战沉淀

本技能指导你撰写符合 To B 项目标准的产品需求文档（PRD）。文档分为三个部分：**需求分析**、**原型说明**、**附录**。每个部分包含明确的子模块和输出要求。

---

## 工作流程

收到 PRD 撰写请求后，按以下顺序执行：

1. **采集需求信息** — 向用户确认项目背景、目标用户、核心业务场景、迭代范围
2. **按框架逐模块输出** — 按照下方的三部分结构，依序输出各模块内容
3. **输出完整 PRD 文档** — 将所有模块整合为一份完整的 Markdown 文档
4. **质量自检** — 使用 `references/checklist.md` 进行交付前自检

在撰写过程中，随时与用户确认关键决策点（如需求优先级判定、业务规则歧义、版本边界划分）。不要自行猜测业务逻辑。

---

## When to Use

- 用户需要编写完整的产品需求文档（PRD）
- 从零梳理一个新项目/新模块的业务需求
- 需要输出结构化的功能清单、用户场景、业务流程
- 已有需求素材（客户沟通记录、会议纪要、竞品分析），需要转化为正式文档
- 需要对接研发团队，输出可直接进入技术方案设计的交付物
- 已有 PRD 需要补充缺失模块（如非功能性需求、交互状态说明）

**When NOT to Use:**
- 用户只是做售前调研或行业分析 → 使用 `hv-analysis` 或 `requirements-pipeline` 的 P0 阶段
- 用户只是做功能模块拆解但还没到写 PRD 的阶段 → 使用 `requirements-pipeline` 的 P2 阶段
- 用户需要的是一份商务方案/投标文件 → 使用专门的方案/标书技能
- 用户只需要一个简单的功能说明（2-3 段话就能说清的事） → 直接写，不需要套 PRD 框架

## 文档元信息

每份 PRD 文档顶部必须包含以下元信息表：

```markdown
| 项目       | 内容                        |
|------------|----------------------------|
| 文档名称   | [项目名称] 产品需求文档 Vx.x |
| 产品负责人 |                            |
| 创建日期   | [YYYY-MM-DD]                |
| 最后更新   | [YYYY-MM-DD]                |
| 文档状态   | 草稿 / 评审中 / 已定稿       |
| 当前版本   | Vx.x                        |
```

文档状态严格使用三态：草稿 → 评审中 → 已定稿。状态变更时必须同步更新最后更新日期。

元信息表不包含“评审人”行。“产品负责人”一行保留展示但默认为空：除非用户明确提供姓名，否则不得填写或臆测。

## 第一部分：需求分析

需求分析是 PRD 的核心，目的是让所有干系人对"做什么、为什么做、怎么做"达成共识。本部分从宏观到微观层层递进。

### 1.1 背景与目标

本节回答"为什么有这个需求"以及"要达成什么目标"。

**必须包含的要素**：

- **需求背景**：这个需求从哪里来？谁提出的？是客户反馈、市场竞争、内部运营驱动还是战略规划？用 2-3 段话把来龙去脉讲清楚，让一个新加入项目的人也能快速理解。
- **需求真伪判断**：简要说明为什么判定这是一个真需求。如果存在争议点，列出正反论据。避免"领导说的所以做"这种循环论证。
- **需求目标**：从四个维度分层阐述（不是每个项目都有全部四个，按实际情况选取）：
  - **业务目标**：解决什么业务问题，带来什么业务价值
  - **市场目标**：面向什么市场、什么客户群体、竞争定位
  - **运营目标**：降本增效指标、SLA 改善、流程优化等可量化目标
  - **产品目标**：功能完整性、用户体验、技术债务清理等
- **产品迭代节奏**：以路标（Roadmap）形式列出各版本规划，说明各版本的核心目标和关键功能边界。格式示例：

```markdown
| 版本  | 核心目标               | 关键功能                          | 计划周期     |
|-------|----------------------|----------------------------------|-------------|
| V1.0  | 跑通核心业务闭环        | 基础 CRUD + 审批流程               | 2026-Q2     |
| V2.0  | 提升运营效率            | 数据看板 + 批量操作 + 通知集成      | 2026-Q3     |
| V3.0  | 开放生态对接            | OpenAPI + 第三方系统集成           | 2026-Q4     |
```

- **本次迭代范围**：明确本次版本要做什么、**不做什么**。"不做"的边界和"做"一样重要——它避免需求蔓延。

### 1.2 用户场景梳理

本节回答"谁在什么场景下用这个系统"。

**第一步：定义目标用户角色**

对系统涉及的所有用户角色进行梳理和定义。To B 系统通常涉及多层级、多角色交叉，务必覆盖完整。

```markdown
| 角色名称     | 角色描述                    | 使用频率    | 核心诉求               |
|-------------|----------------------------|------------|----------------------|
| 系统管理员   | 负责平台配置与用户管理         | 低频       | 快速配置，异常处理      |
| 业务主管     | 审批流程、查看统计报表         | 每日       | 效率、数据准确性        |
| 一线操作员   | 日常业务录入与处理             | 高频       | 操作简便，减少出错      |
```

**第二步：梳理用户核心目标与场景**

每个用户角色可能有多个核心目标。针对每个核心目标，描述其对应的业务场景，并绘制用户场景交互流程图。

场景描述应包含：
- **角色**：谁在操作
- **目标**：他想完成什么
- **前置条件**：需要什么前提（权限、数据、状态）
- **典型路径**：正常情况下的操作步骤
- **异常路径**：关键异常场景（权限不足、数据缺失、并发冲突等）
- **结果**：操作完成后的系统状态变化

> 对于核心场景，建议使用流程图呈现。非核心场景用文字描述即可。重点场景和非重点场景的划分由产品经理判断，原则是：涉及金钱、权限、数据安全的场景必须详细。

### 1.3 业务流程图

本节用可视化方式呈现业务全貌和流转逻辑，供架构师进行架构设计，研发进行技术选型和库表设计参考，同时也是产品自检业务逻辑是否有遗漏的工具。

**1）整体业务流程图**

宏观视角，展示整个业务系统的全局流程：
- 业务的输入源（数据从哪来）
- 核心处理模块（经过哪些环节）
- 输出结果（产出什么、流向哪里）
- 模块间的依赖和流向关系

使用 Mermaid 的 `graph TD`（从上到下）或 `graph LR`（从左到右）绘制。节点按模块分组，用子图（subgraph）表示系统边界。

**2）业务流程泳道图**

微观视角，展示各角色在业务中的协作关系：
- **横向**：各关键用户角色 / 系统
- **纵向**：按时间顺序排列的业务节点
- 明确标注每个节点的参与角色、决策分支、数据流向
- 形成一个完整的业务流程闭环

泳道图的核心价值：让所有人都能看清"谁在什么时候做什么事"、"业务在哪些角色之间流转"。

> 建议使用 Mermaid 的 `sequenceDiagram` 或标准泳道图呈现。如果业务复杂，可以按子流程拆分多张图。

### 1.4 信息架构图

本节从信息组织和系统结构两个维度描绘系统全貌。

**1）系统架构图**

技术视角的系统架构，按以下维度分层展示（根据项目实际复杂度选取）：
- **业务层**：业务模块划分
- **应用层**：服务/应用划分
- **数据层**：数据存储、数据流
- **技术层**：技术栈、中间件
- **部署层**：部署拓扑
- **安全层**：安全策略、权限体系

> 系统架构图主要为技术团队服务。产品经理通常重点关注业务层和应用层，技术层/部署层可与架构师协作补充。

**2）信息结构图**

产品视角的信息组织——不画服务器、不画技术栈，核心关注：
- **信息怎么组织**：哪些信息聚合在一起，层级关系如何
- **用户怎么找到**：导航路径、搜索维度
- **页面怎么跳转**：页面层级、跳转关系

输出内容包含：
- **核心结构**：用树状图展示系统的前端页面层级（一级菜单 → 二级菜单 → 页面 → 子页面/弹窗）
- **页面与模块说明**：每个叶子节点对应的页面功能概述

```markdown
示例：
├── 工作台（首页）
│   ├── 待办事项
│   ├── 数据概览
│   └── 快捷入口
├── 业务管理
│   ├── 订单管理
│   │   ├── 全部订单（列表页）
│   │   ├── 订单详情（详情页）
│   │   └── 新建订单（表单页）
│   └── 客户管理
│       ├── 客户列表
│       └── 客户画像
└── 系统设置
    ├── 角色管理
    ├── 权限配置
    └── 操作日志
```

### 1.5 需求清单

本节对本期迭代的所有需求进行清单化管理。

**需求清单表**：

```markdown
| 优先级 | 需求编号 | 需求名称     | 所属模块   | 主要功能说明               | 关联角色       |
|-------|---------|-------------|-----------|--------------------------|--------------|
| P0    | REQ-001 | 用户登录认证  | 系统设置   | 账号密码登录 + SSO 集成     | 全部角色      |
| P1    | REQ-002 | 订单创建     | 业务管理   | 表单录入 + 草稿保存 + 提交   | 一线操作员    |
| P2    | REQ-003 | 数据看板     | 工作台     | 核心指标展示 + 趋势图        | 业务主管      |
```

优先级定义：
- **P0（必须有）**：核心业务闭环所需，缺失则产品不可用
- **P1（应该有）**：重要功能，影响核心体验但不阻塞主流程
- **P2（可以有）**：锦上添花，可在后续版本迭代
- **P3（暂不做）**：已识别但明确本期不做，记录备查

**需求影响点说明**：如果本次需求变更会影响到已有功能、已有数据或已有接口，必须单独列出影响范围和影响程度。

### 1.6 非功能性需求（补充）

To B 系统的稳定性、安全性、合规性往往和功能同等重要。根据项目实际情况，从以下维度评估和说明：

| 维度       | 典型关注点                                          |
|------------|---------------------------------------------------|
| **性能**   | 并发量预估、响应时间要求、大数据量场景处理               |
| **安全**   | 数据加密、权限控制粒度、审计日志、等保/合规要求           |
| **兼容性** | 浏览器版本、操作系统、移动端适配、屏幕分辨率             |
| **可用性** | SLA 要求、容灾方案、数据备份策略                       |
| **集成**   | 与现有系统的接口对接、数据迁移、第三方服务依赖            |

> 不是每个项目都需要面面俱到。根据项目规模和客户要求，选择适用的维度重点说明。小项目可以简写为一段文字概述。

### 1.7 数据指标设计（补充）

定义产品上线后如何衡量成功。指标设计遵循"北极星指标 + 辅助指标"模式：

- **北极星指标**：1 个核心指标，直接衡量产品是否达成业务目标
- **辅助指标**：3-5 个过程指标，从不同维度补充衡量

```markdown
示例：
| 指标类型     | 指标名称       | 定义                    | 目标值        | 数据来源  |
|-------------|---------------|------------------------|--------------|----------|
| 北极星指标   | 日活跃用户数    | 每日至少完成 1 次核心操作   | ≥200         | 埋点     |
| 辅助指标     | 任务完成率     | 发起的任务中成功完成的占比   | ≥85%         | 业务数据  |
| 辅助指标     | 平均处理时长    | 从创建到完结的平均耗时      | ≤2 工作日     | 业务数据  |
| 辅助指标     | 系统错误率     | 操作中触发系统错误的频率     | ≤0.5%        | 监控     |
```

> 如果项目尚处于 MVP 阶段，指标可以先定义框架，数值待上线后根据实际数据校准。

## 第二部分：原型说明

原型说明是给设计师和研发的技术交付物，需要精确到页面、字段、交互、状态。

### 2.1 变更说明

本节为整个需求文档的变更记录表，贯穿文档生命周期。每次修改必须追加记录，方便快速溯源。

```markdown
| 变更日期     | 变更版本 | 变更背景                | 变更功能   | 变更位置       | 变更内容详情                    | 变更人 |
|-------------|---------|------------------------|-----------|---------------|-------------------------------|-------|
| 2026-04-10  | V1.1    | 客户反馈审批层级不够灵活  | 审批流程   | 3.2.1 审批配置 | 新增多级审批支持，最多支持 5 级   | liuyz |
```

> 变更说明表建议放在原型说明部分的最顶部，阅读者打开文档第一眼就能看到最新变更。

### 2.2 公共部分说明

本节统一定义全局通用的设计规范和公共组件，避免在后续功能模块说明中重复描述，同时便于研发设计全局公共变量。

**典型的公共部分包含**：

- **菜单与导航规则**：菜单层级结构、默认展开/收起规则、面包屑规则
- **权限体系说明**：角色与权限关系矩阵、数据权限规则（如按部门/区域隔离）、菜单权限与按钮权限的区分
- **通知消息规则**：系统通知触发条件、通知渠道（站内信/邮件/短信/企微/钉钉）、通知模板
- **全局交互规范**：
  - 列表页通用行为（分页、排序、筛选、搜索的默认规则）
  - 表单通用规则（必填标识、校验时机、保存与提交的区别）
  - 弹窗规则（确认弹窗、操作弹窗、抽屉弹窗的使用场景区分）
  - 批量操作规则（勾选逻辑、跨页勾选、批量操作权限）
- **全局状态定义**：系统中反复出现的状态枚举（如：草稿/待审批/已通过/已驳回/已撤回）
- **数据字典**：全局通用的枚举值定义（如行政区划、行业分类等）

> 公共部分不求多求准。宁可一开始少写，后续随功能模块推进时补充，也不要凭空编造规则。

### 2.3 功能模块说明

本节是 PRD 的核心交付内容，按照菜单结构逐一说明每个功能模块的详细设计。

**组织结构**：按"大菜单 → 子菜单 → 子功能"的层级拆分。

**每个功能模块应包含**：

#### 2.3.1 模块流程图

在具体页面说明之前，先用流程图展示本模块的业务流程：
- 用户操作路径
- 系统自动处理逻辑
- 关键决策分支
- 状态流转

#### 2.3.2 页面说明

逐页描述每个页面的布局和内容，包含：

**列表页**：
- 筛选条件（字段、类型、默认值）
- 列表字段（字段名、数据类型、排序规则、是否可点击）
- 操作列（每个操作按钮的显示条件、点击行为）
- 批量操作（如有）
- 分页规则

**详情页**：
- 信息分组和布局
- 各字段的展示规则
- 操作按钮及其业务逻辑
- 关联数据展示

**表单页**（新增/编辑）：
- 表单字段清单表：

```markdown
| 字段名称  | 字段类型     | 是否必填 | 校验规则            | 默认值 | 备注说明            |
|----------|-------------|---------|--------------------|----|-------------------|
| 项目名称  | 文本输入      | 是      | 长度 1-50 字符       | 空  | 不允许特殊字符       |
| 负责人    | 人员选择器    | 是      | 仅限本部门           | 空  | 支持搜索            |
| 开始日期  | 日期选择器    | 是      | 不早于今天           | 今天 | —                  |
| 附件     | 文件上传      | 否      | PDF/Word, ≤20MB    | 空  | 最多 5 个           |
```

- 表单联动规则（字段 A 的值影响字段 B 的显示/可选范围）
- 保存与提交的区别（如有）

#### 2.3.3 交互状态说明（补充）

每个页面需要考虑以下交互状态，确保设计覆盖完整：

| 状态       | 说明                                 | 处理方式              |
|-----------|--------------------------------------|---------------------|
| 加载中     | 页面/数据正在加载                      | 展示骨架屏或加载动画   |
| 空状态     | 列表无数据或搜索无结果                  | 展示引导文案和操作入口  |
| 错误状态   | 接口异常或操作失败                      | 展示错误提示和重试入口  |
| 权限不足   | 用户无权访问某页面或操作                 | 展示无权限提示页       |
| 并发冲突   | 多人同时编辑同一数据                    | 乐观锁/提示后覆盖     |

> 空状态和错误状态是 To B 系统体验的重灾区。每个列表页和表单页都应该有对应的空状态和错误状态设计。

#### 2.3.4 接口约束说明（补充，按需）

对于涉及系统间对接或复杂数据处理的模块，补充关键接口约束：
- 数据格式要求
- 调用频率限制
- 超时处理策略
- 幂等性要求

## 写作原则

1. **先理解再动笔**：不清楚的业务逻辑主动向用户确认，不要凭想象填充。To B 业务的特殊性在于每个客户的流程都可能不同。
2. **够用就好**：小项目不要硬套完整框架。附录和补充模块根据实际复杂度选用，MVP 阶段可以只输出第一部分和第二部分的核心内容。
3. **说人话**：功能说明要让研发直接能用来写代码。"支持灵活配置"不是需求，"支持管理员在后台配置最多 5 级审批层级，每级可选择审批人或审批角色"才是。
4. **标注边界**：每个功能说明都要尽可能清楚地标注本期做什么、不做什么。边界模糊是需求变更的最大元凶。
5. **流程先行**：先画流程图，再写页面说明。流程图能暴露 80% 的逻辑遗漏。
6. **状态穷举**：列表页的每种筛选组合、表单的每种校验场景、流程的每个分支都要考虑到。遗漏的状态 = 留给研发的坑。

## Anti-Rationalization

以下是撰写 PRD 过程中常见的偷懒借口。如果你发现自己正在产生这些念头，立刻停下来纠正。

| Agent 的借口 | 现实 |
|---|---|
| "用户给的信息太少了，我先按自己理解写，后面再确认" | 这是 PRD 质量最大的杀手。不清楚的地方必须**立刻向用户确认**，哪怕要问 5 个问题。凭想象填充的需求 = 返工的种子。 |
| "这个项目很简单，不需要画业务流程图" | 流程图不是给复杂项目用的装饰。一个看似简单的 CRUD 可能隐藏 3 个审批分支和 5 种异常状态。画图才能暴露遗漏。 |
| "用户角色就两三个，场景分析可以简写" | 角色少不代表场景简单。每个角色可能有 2-3 个核心目标，每个目标有正常路径和异常路径。简写 = 留坑。 |
| "非功能性需求和数据指标不重要，先跳过" | To B 项目翻车 60% 是因为性能、安全、并发没提前考虑。这些不是"补充"，是核心。 |
| "表单字段太多了，我列几个关键字段就行" | 研发拿到 PRD 第一件事就是看字段清单表来设计库表。你漏一个字段，研发就多一次返工。**穷举，不要挑选**。 |
| "交互状态（空状态、加载中、错误）不用每个页面都写" | 这些状态是用户体验的底线。每个列表页、每个表单页都必须覆盖。遗漏的状态 = 用户看到的白屏。 |

---

## Red Flags

如果在撰写过程中出现以下信号，说明正在偏离正轨，需要立即自查：

- 输出了大段文字但没有任何流程图或表格——PRD 不是散文，可视化是核心
- 需求清单中所有需求都是 P0——没有优先级等于没有优先级
- 功能描述中出现"灵活"、"丰富"、"优化"等模糊词但没有具体约束值
- 写了"支持多种XX"但没有穷举到底支持哪几种
- 只描述了正常流程，没有异常路径和边界条件
- 用户场景中只有操作步骤、没有前置条件和预期结果
- 编造了用户没有提供的业务规则（如自行假设了审批层级、权限规则）
- 表单字段清单表缺少校验规则或默认值列
- 整份文档没有出现"不做"——没有明确的版本边界
