# 排期规则与工期估算指引

> 本文件定义 `project-manage` Skill 中工期估算与排期推算的规则，确保排期合理、依赖闭环、可追溯。

---

## 一、工期单位

- **默认单位**：自然日（d，含周末）
- 如需工作日估算（W-Day，不含周末），需在调用时声明
- 工期 ≤ 0 视为非法，必须 ≥ 1d

---

## 二、里程碑默认工期

| 里程碑 | 默认工期 | 调整规则 |
|---|---|---|
| 需求评审 | 1d | 大型项目（功能数 > 20）可延长至 2d |
| 技术方案评审 | 2d | 多模块/微服务架构延长至 3-5d |
| UI 评审 | 2d | 终端数 × 1d（≥ 2d） |
| 测试用例评审 | 2d | 功能数 > 15 时延长至 3d |
| 开发提测 | 见 § 三 | 由开发子任务累计估算 |
| 测试完成 | 见 § 四 | 由测试用例数估算 |
| 验收完成 | 1d | 功能数 > 20 时延长至 2d |
| 发版上线 | 1d | 灰度策略复杂时延长至 2d |
| 生产验证 | 1d | 关键业务延长至 2d |
| 业务培训 | 1d | 受众 > 50 人或跨多区域时延长至 2-3d |

## 三、开发子任务工期估算

### 基础规则

按"功能复杂度"三档估算：

| 复杂度 | 特征 | 工期 |
|---|---|---|
| **简单** | 单一字段、配置项、静态展示 | 1d |
| **中等** | 含交互逻辑、接口对接、状态流转 | 2-3d |
| **复杂** | 含算法、并发、第三方对接、性能优化 | 3-5d |

### 复杂度判定依据（按 PRD "五、需求功能详述"）

- **技术难点分析**中出现"算法""并发""分布式""实时""高并发""对账" → 复杂
- 涉及 2 个及以上模块联动、含状态机 → 中等或复杂
- 仅前端展示 + 单接口调用 → 简单或中等
- 仅表单提交、CRUD → 简单

### 调整因子

- **新终端/新框架**：基础工期 × 1.5
- **多人协作**：基础工期 × 1.2
- **未知/未确认**：标「待补充」，不擅自估算

### 累计估算

- 「开发提测」里程碑工期 = 所有开发子任务的**最长链路工期**（关键路径），不是简单累加
- 假设可并行的子任务，应在「依赖关系」中体现串并行

## 四、测试工期估算

| 估算维度 | 公式 |
|---|---|
| 测试用例数 | 从 PRD "五、需求功能详述" 中的测试用例数累加 |
| 测试工期 | 测试用例数 × 0.1d ~ 0.2d（按用例复杂度） |
| 默认下限 | 至少 3d |
| 回归测试 | + 1-2d（核心功能回归） |

如 PRD 未明确给出测试用例数，按功能数 × 5（每功能平均 5 条用例）估算。

## 五、排期推算规则

### 1. 起始日

- 用户通过 `--start=YYYY-MM-DD` 提供
- 未提供时必须询问，**不得擅自假设**

### 2. 推算算法

```
对于每个任务（按依赖关系拓扑序）：
  开始时间 = max(所有前置任务的结束时间 + 1d, 项目起始日 + 累计前置工期)
  结束时间 = 开始时间 + 工期 - 1d
```

注：使用 `scripts/calc_schedule.py` 自动推算。

### 3. 关键路径

关键路径 = 从「需求评审」到「业务培训」的最长链路，决定项目总工期。

### 4. 排期合理性校验

- 所有任务的开始时间 ≤ 结束时间
- 后置任务的开始时间 ≥ 前置任务的结束时间
- 关键路径上的工期累加 = 项目总工期
- 依赖链必须闭环（无循环）

## 七、异常处理

| 场景 | 处理 |
|---|---|
| 工期估算信息不足 | 标「待补充」，不擅自假设 |
| 依赖关系形成循环 | 报错，提示用户检查依赖 |
| 起始日早于今日 | 提醒用户确认是否补算历史工期 |
| 里程碑工期超出预期 | 在「备注」列说明原因 |
| 关键路径上工期 < 1d | 至少设为 1d |
