# 文案规范（Voice & Tone）

> 界面文案是产品的一部分，不是填充物。政务/企业系统的底线：**中性、准确、不甩锅、不吓人、不暴露内部实现**。

---

## 一、语气基线

| 场景 | 应该 | 不应该 |
|---|---|---|
| 常规说明 | 陈述事实：「数据每天 06:00 同步」 | 「系统会自动帮您同步哦～」 |
| 错误提示 | 中性：「保存失败，请重试」 | 「您操作有误」「非法输入」 |
| 权限不足 | 说明原因与出路：「缺少审核权限，请联系管理员」 | 「无权限」两个字了事 |
| 危险操作 | 讲清后果：「作废后不可恢复」 | 「确定吗？」 |
| 禁用态 | 解释条件：「需先完成实名认证」 | 「不可用」 |

禁忌：

- 不用感叹号堆情绪（「保存成功！！！」）。
- 不用技术黑话（`500`、`null`、`undefined`、`SQL`、`token 失效`）直接示人。
- 不指责用户（「您输入错误」→「手机号格式不正确」）。
- 不暴露内部标识（菜单 ID、字段名、需求编号）——这条与 SKILL.md「UI 卫生」一致。

## 二、错误文案三段式

**发生了什么 + 为什么 + 怎么办**

| 差 | 好 |
|---|---|
| 操作失败 | 保存失败，网络连接超时（3 次重试后仍未成功），请检查网络或稍后重试 |
| 提交错误 | 提交失败：附件超过 20MB，请压缩后重新上传 |
| 数据异常 | 该记录已被他人删除，无法编辑。请刷新列表查看最新数据 |

长度：标题 ≤ 20 字，说明 ≤ 60 字；细节（错误码、时间、请求 ID）放到「详情」折叠区，方便排障但不干扰。

## 三、按钮与动作动词表

| 动作 | 用词 | 说明 |
|---|---|---|
| 保存并留在本页 | 保存 | 弹窗表单、行内编辑 |
| 保存并离开 | 保存并关闭 / 保存并返回 | 避免用户猜 |
| 提交审批 | 提交 | 与「保存」区分，提交后进入流程 |
| 二次确认 | 确定 | 仅在确认弹窗里用，正文写清后果 |
| 删除单条 | 删除 | 危险色 |
| 批量删除 | 批量删除 | 正文写清条数 |
| 移除关联关系 | 移除 | 不删数据本体时不要用「删除」 |
| 不可逆作废 | 作废 | 正文写「不可恢复」 |

同一个动作在全系统只能有一种叫法：「新建 / 新增 / 创建」选一个，不要混用。

## 四、空态与状态文案模板

| 场景 | 模板 |
|---|---|
| 首次空 | 还没有{对象}；新建后可{价值} |
| 无结果 | 没有符合条件的{对象}；试试清除筛选 |
| 无权限 | 暂无{对象}查看权限（范围：{范围}）；可申请权限 |
| 出错 | 加载失败；{原因}；重试 |
| 状态 Tag | 用业务词：待受理 / 审核中 / 已办结 / 已驳回（不要「状态1」） |
| 成功 Toast | 已保存 / 已提交 / 已删除 3 条（不要「操作成功」） |

## 五、数字、日期、单位

详细格式见 `components-guide.md`「数据展示规范」，文案侧补充：

- 单位写在列头或轴名，不在每个单元格重复；同一列单位必须统一。
- 百分比保留 1 位小数；金额千分位 + 2 位小数。
- 相对时间（「3 分钟前」）只在 ≤ 7 天内使用，更早用绝对时间 `YYYY-MM-DD HH:mm`。
- 时区：跨时区系统统一展示 `GMT+8`，并在页脚或帮助里说明。

---

## 六、中英混排与标点

- 中文正文用全角标点，中英文之间留半角空格（「共 12 条记录」）。
- 专有名词大小写统一：`ID`、`API`、`URL`、`PDF`，不要 `id/ID` 混用。
- 不要在中文句子中夹英文动词（「你去 submit 一下」）。

---

## 七、自查清单

1. 错误文案是否包含「发生了什么 + 为什么 + 怎么办」？
2. 是否出现技术黑话、堆栈、内部 ID、需求编号？
3. 同一动作是否全系统同一个词（新建/新增/创建没有混用）？
4. 危险操作是否写清后果与不可恢复性？
5. 成功提示是否具体（「已删除 3 条」而不是「操作成功」）？
6. 空态文案是否指向下一步动作？
