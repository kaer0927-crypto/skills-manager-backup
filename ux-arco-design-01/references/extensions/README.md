# 扩展与例外登记（Extensions）

> 规范的边界是「已覆盖的场景」。当业务出现规范没写的东西（审批流画布、甘特图、大屏之外的复杂可视化、行业专有控件），
> **不要硬套骨架，也不要偷偷自造一套**——走这里的登记流程。

---

## 一、什么时候必须登记

| 情况 | 处理 |
|---|---|
| 首页/表单/列表/详情/结果/异常页 | 已有骨架，直接用，不登记 |
| 需要一个规范没有的**交互模式**（如时间轴排班、流程编排、地图钻取） | 登记，新增 `extensions/<pattern>.md` |
| 需要在规范之外**新增设计 Token / 组件** | 登记，并说明为何现有 Token 不够 |
| 确实要**违反**某条硬规则 | 登记，写明理由、影响范围、审批人；未登记不得违反 |

以下硬规则**永远不能**通过扩展绕开：

- 弹窗面板必须实色（禁止玻璃半透明面板）
- 危险操作必须有确认与后果说明
- 权限三态（隐藏/禁用/403）必须明确
- 敏感字段必须默认脱敏
- 同一界面只用一个主题

---

## 二、登记模板（复制到 `extensions/<pattern>.md`）

```md
# <模式名>

## 1. 场景
什么业务、什么页面、用户要完成什么任务。

## 2. 为什么现有规范不适用
指出最接近的骨架（文件 + 章节），说明缺什么能力，而不是「不好看」。

## 3. 结构
ASCII 骨架 / 关键层级，标注区域尺寸。

## 4. 交互
点击、hover、键盘、空态、加载、错误、禁用原因。

## 5. 新增 Token / 组件
| 名称 | 值 / 来源 | 为什么现有 Token 不够 |

## 6. 可访问性
键盘路径、对比度、焦点、播报。

## 7. 是否回灌主规范
是 / 否；若「是」，需要改哪些文件、由谁评审。
```

---

## 三、命名与存放

```
references/extensions/
├─ README.md                ← 本文件
├─ approval-designer.md     ← 模式名用英文 kebab-case
└─ schedule-board.md
```

- 一个文件只描述**一个模式**，不要写成大杂烩。
- 模式名与组件名一致，便于检索。
- 新增模式后，在 `component-catalog.md` 的「扩展模式」表里加一行索引。

---

## 四、回灌机制

- 同一模式被 **2 个以上项目**复用，或连续 3 次被要求实现 → 提为正式规范，合并进 `pages-guide.md` / `components-guide.md`。
- 回灌时同步更新：目录索引、SKILL.md 导航、自查清单、`scripts/check-consistency.mjs`（如涉及一致性规则）。
- 回灌后删除 `extensions/` 里的临时条目，避免双份事实源。
