# P1 需求理解与技术方案

> **角色**：架构师。本阶段只做分析与方案设计，不写代码。
> **产出**：`implementation_plan.md`

## 前置输入

- 需求文档（PRD / 会议纪要 / 修改说明 / 参考系统截图，任意形式）
- 项目现有代码（重构/迭代场景）
- `Memory.md`（如存在，先读，了解项目历史）

## 执行步骤

### Step 1.1 — 全量信息收集

1. 读 `Memory.md`（如有）
2. 读需求文档全文（**禁止只看文件名就写方案**）
3. 扫描现有代码：`src/` 目录树 + `package.json` + 确认实际技术栈
4. 用户给了参考系统 → 有浏览器工具则访问分析交互模式；无则请用户提供关键页面截图

### Step 1.2 — 业务理解校准

| 维度 | 理解 |
|------|------|
| 产品定位 | [一句话] |
| 核心链路 | [主流程] |
| 与竞品差异 | [差异化价值] |
| 用户角色模型 | [各角色操作场景] |
| 数据闭环 | [数据如何流转反馈] |

🔴 GATE：**必须暂停让用户校准**。存在 ≥2 个不确定点时列出来逐个问清。

### Step 1.3 — 修改要点结构化

| # | 要求 | 影响范围 | 描述 |
|---|------|---------|------|
| 1-1 | [需求名] | 架构级/模块级/组件级 | [详细描述] |

### Step 1.4 — 破坏性变更与已确认项

明确标出两类内容：

- **破坏性变更（User Review Required）**：会废除/大改现有功能的变更 + 保底方案
- **已确认项**：用户明确表过态的决策

### Step 1.5 — 文件变更清单（方案核心）

按 Phase 分组列出每个变更文件：

```markdown
### Phase N: [阶段名]

#### [NEW|MODIFY] src/相对路径/文件名
- 组件结构 / 数据来源（store state 或 mock）/ 交互行为 / 样式要求 / 与其他模块的关系
```

标注 `[NEW]` 新建 / `[MODIFY]` 修改，路径用**项目内相对路径**。

### Step 1.6 — 技术决策汇总

| 决策项 | 方案 | 理由 |
|--------|------|------|

### Step 1.7 — 验证方案

- 自动化验证：TS 编译命令、dev 启动命令
- 浏览器验证：逐项列出可操作的验证点（后续 P5 直接取用）

## 交付物：`implementation_plan.md`

章节结构：背景（含业务理解校准）→ 修改要点全景 → User Review Required → Proposed Changes（按 Phase 分组）→ 技术决策汇总 → Verification Plan。

## 阻断规则

- 用户未提供任何需求信息 → 追问，**不得自行假设需求**
- 业务理解不确定点 ≥2 → 暂停校准
- 🔴 GATE：方案产出后必须等用户确认才能进 P2
