# Skill：需求分析（requirements-analysis）

## 触发词
/requirements-analysis

## 一句话描述
在 PRD 撰写前对需求进行结构化调研、分析和确认，严格按五段式模板（需求背景→目标确认→流程分析→功能拆解→待确认事项）输出需求分析文档，**严格按下文输出模板逐块填充**。

## 输入约定
- **必填**：需求背景、目标、分析范围（来自用户对话或 `--requirement` 输入文件）
- **必填**：输出文件名前缀（`--output=<name>` 或基于需求主题命名），用于命名需求分析文档
- **可选**：当前系统现状文件（`--system-status=<path>`），用于在拆解功能清单时对照现有系统
  - 若提供：在功能拆解时对照现有终端/服务，识别复用与改造点
  - 若未提供：直接基于需求拆解功能清单，不做现有系统对照
- **可选**：现有需求文档（`--requirement=<path>`），当用户希望基于已有文档补充分析时使用

## 执行步骤
1. **收集输入**：若用户提供 `--requirement` 或 `--system-status` 文件，先读取；否则基于对话内容或其他输入的文件内容
2. **理解需求背景**：明确需求的来源、现状痛点、受影响用户/角色、不做的后果
3. **确认需求目标**：与用户/干系人确认核心目标和期望成果，必须具体可衡量
4. **分析业务流程**：用 Mermaid 绘制**核心业务流程**，每个节点明确输入输出
5. **拆解功能清单**：按"终端/模块/功能/描述/优先级"表格输出，优先级使用 Must / Should / Could / Won't
6. **（可选）系统对照**：若提供了 `--system-status`，在功能拆解中标注复用现有能力 / 新增能力 / 改造点
7. **识别待确认事项**：列出尚未与干系人确认的内容，所有未确认项不得在 PRD 中自行假设
8. **输出文档**：保存到**与输入文件相同的目录**下，命名 `{output_basename}-需求分析.md`，严格按 `reference/analysis-template.md` 模板逐块填充
   - 若提供了 `--requirement=<path>`：输出到该文件所在目录
   - 若未提供输入文件（基于对话内容分析）：输出到当前工作目录

---

## 输出模板（必须严格遵守）

> **强制要求**：输出的 Markdown 文件**必须严格按 `reference/analysis-template.md` 模板填充**。
> - 模板的所有一级标题（`#`、`##`、`###`）的层级和文字**不得更改**
> - 所有占位符必须替换为实际内容；没有内容的项填 `N/A` 或 `无`，未确认项标"待确认"
> - 5 大板块**顺序固定、缺一不可**
> - 表格列定义、字段顺序**不得增删**

**模板文件**：`reference/analysis-template.md`（五段式结构、表格列定义、字段说明均以此文件为准；如有歧义以模板文件为权威）

---

## 输出契约

1. **输出数量**：**只输出 1 个 Markdown 文件**，严禁拆分多个文件
2. **输出路径**：**与输入文件相同的目录**，命名 `{output_basename}-需求分析.md`（未提供输入文件时输出到当前工作目录）
3. **模板严格性**：上方"输出模板"中的所有标题层级、表格列、字段顺序**不得更改**
4. **空值处理**：没有内容的项填 `N/A` 或 `无`，未确认项必须标"待确认"，**禁止留空、禁止自行假设**
5. **可选输入处理（`--system-status`）**：
   - **提供时**：在"四、功能拆解清单"中标注每条功能与现有系统的对照关系，三选一：
     - **复用**：完全沿用现有能力，不做改动
     - **新增**：现有系统无此能力，需新建
     - **改造**：基于现有能力做接口/逻辑变更
   - **未提供时**：跳过系统对照，直接基于需求拆解，不在"功能描述"里假设"复用现有 XX"

---

## 约束

- ✅ **模板严格性**：五段式结构顺序、标题层级、表格列定义**不得更改**
- ✅ **干系人确认**：未与干系人确认的内容必须标"待确认"，不得自行假设
- ✅ **Mermaid 强制**：业务流程必须用 Mermaid 语法绘制
- ✅ **结构化输出**：功能拆解清单必须按"终端/模块/功能/描述/优先级"表格输出
- ✅ **优先级规范**：使用 Must / Should / Could / Won't 四级（与 analysis-template.md 保持一致）
- ✅ **数据流向闭环**：每个流程节点明确输入和输出
- ✅ **可选输入处理**：`--system-status` 提供时做现有系统对照，未提供时直接拆解
- ❌ **禁止**：跳过需求不清晰时的确认（必须主动询问用户）
- ❌ **禁止**：编造未确认的需求细节（所有未确认项必须标"待确认"）
- ❌ **禁止**：省略任何一级标题、合并板块、用自由格式替代表格
- ❌ **禁止**：模糊表述（"可能"、"大概"、"待定"不得出现在最终决策中）
- ❌ **禁止**：输出多个 Markdown 文件
