# 操作手册生成

## 1. 这个 Skill 干什么

把一个业务系统的"怎么用"写成最终用户能照着点的手册。读者不是开发，是机关里的资产管理员、公车调度员、办公室经办人、审批领导。

**核心原则：先看界面再动笔，不脑补。** 任何按钮名、菜单路径、字段名、弹窗文案，都必须来自用户提供的原型、截图、PRD 或需求文档。看不到就问，不要自己编一个"保存按钮"。

## 2. 动笔前必须先确认的 4 件事

按顺序问用户（一次问完，不要挤牙膏）：

1. **系统叫什么名字、给谁用**？（例：XX 市机关事务资产云平台 / 资产管理员 + 审批领导）
2. **有哪些角色**？常见组合：系统管理员、业务经办人、部门审批人、单位管理员、领导查询端。每个角色能干什么要列清楚。
3. **界面素材在哪**？Axure 导出 HTML 目录、Figma 链接、截图包、还是 PRD 文档？没有素材就只列大纲，不要直接写正文。
4. **导出格式**？默认 Markdown 源文件 + Word（用 docx skill 导出）。要不要 PDF。

## 3. 写作铁律（每条都要守）

1. **第二人称**。用"您"，不要用"用户可以…"、"操作者需要…"。
2. **界面元素用【】包起来**。按钮、菜单、Tab、字段名、弹窗标题一律【】。例：点击【保存】按钮，在【资产名称】字段输入"公务用车-001"。
3. **每个操作必须四段**：
   - **前置条件**：您已经登录、您有 XX 权限、单据已提交到下一步。
   - **操作路径**：一级菜单 → 二级菜单 → 按钮，一步一步写。
   - **预期结果**：页面弹出"XX成功"提示 / 列表出现新记录 / 单据进入下一节点。
   - **异常处理**：如果【提交】按钮是灰的，先检查必填项；如果提示"编码重复"，联系管理员。
4. **不写"酷炫"、"极简"、"一站式"这种形容词**。手册是工具书，不是营销稿。
5. **不写没看到的功能**。原型里没有的按钮、PRD 里没提的字段，一律不写。发现界面和需求对不上，列出来让用户确认，不要自己选一个版本。
6. **敏感操作要加警示**。删除、批量导入、审批通过、数据导出这类不可逆操作，单独加一行"⚠️ 此操作一经提交不可撤回，请确认无误后再执行"。
7. **政务口吻**。用"请"、"您"，不要用"搞一下"、"点一下就完了"。不要出现英文口语。
8. **截图位置留占位符**。`【截图：登录页全貌，标注账号密码输入框位置】`，让用户后期补图，不要自己生成假截图。

## 4. 手册章节结构（按这个骨架写）

```
封面：
  《{系统名}用户操作手册》
  版本号 V1.0    发布日期：YYYY-MM-DD    编制单位：XXX

1. 系统简介
   1.1 系统定位（一段话：这系统是干嘛的，解决什么事）
   1.2 运行环境（浏览器版本 / APP 最低版本 / 分辨率要求）
   1.3 角色与权限一览表（表格：角色 | 能做什么 | 不能做什么）

2. 通用操作（所有角色都要看）
   2.1 登录与退出
   2.2 修改密码与找回密码
   2.3 首页布局说明（菜单区 / 消息区 / 待办区）
   2.4 通用按钮说明（【保存】【提交】【审批通过】【退回】【导出】分别什么意思）
   2.5 常见提示语含义（"草稿"、"待审批"、"已归档"、"已驳回"）

3. 管理员操作
   3.1 账号与部门管理
       3.1.1 新增单位/部门
       3.1.2 新增账号与分配角色
       3.1.3 启用/禁用账号
   3.2 基础数据维护（字典、编码规则、审批流配置）
   3.3 系统监控（操作日志、登录日志）

4. 业务经办人操作（按模块拆，每个业务一条线）
   4.1 {业务模块 A，例：资产登记}
       4.1.1 新增资产卡片
       4.1.2 编辑与提交审批
       4.1.3 查看我的草稿
   4.2 {业务模块 B，例：资产领用}
       4.2.1 发起领用申请
       4.2.2 跟踪审批进度
       4.2.3 撤回申请

5. 审批人操作
   5.1 处理待办审批（同意/退回/转办）
   5.2 查看已办事项
   5.3 审批意见规范（写什么不写什么）

6. 领导查询端
   6.1 数据看板怎么看
   6.2 报表导出

7. 常见问题 FAQ（10-15 条）
   - 登录提示"账号不存在"怎么办？
   - 提交后发现填错了能改吗？
   - 导出的 Excel 打开是乱码怎么办？
   - 手机上能审批吗？

8. 技术支持
   运维联系人 / 电话 / 邮箱 / 服务时间
```

**注意**：上面是完整骨架，实际项目里没用到的章节直接删掉（比如没有 APP 端就删掉 APP 相关条目），不要为了凑厚度保留空章节。

## 5. 单条操作的标准写法（照这个模板写）

> ### 4.1.1 新增资产卡片
>
> **前置条件**：您已登录系统，且拥有"资产管理员"角色，当前单位已由上级管理员创建。
>
> **操作步骤**：
> 1. 在左侧菜单依次点击【资产管理】→【资产卡片】→【新增】。
> 2. 在【基本信息】区填写：
>    - 【资产分类】：点击下拉框选择"公务用车"。
>    - 【资产名称】：输入"别克 GL8 公务用车"。
>    - 【资产编号】：按规则"DW-年份-序号"自动带出，如需修改请联系系统管理员。
> 3. 在【附件】区点击【上传】，上传车辆行驶证扫描件（≤10MB，PDF/JPG）。
> 4. 点击【保存】存为草稿；点击【提交】直接进入审批流程。
>
> **预期结果**：
> - 点【保存】后页面顶部出现"草稿保存成功"提示，列表中状态显示"草稿"。
> - 点【提交】后提示"提交成功，已发送至部门审批人"，状态变为"待审批"，且您不能再编辑。
>
> **异常与注意事项**：
> - 【提交】按钮灰色不可点：检查红色必填项是否全部填写。
> - ⚠️ 资产编号一旦提交审批不可修改，提交前请双人核对。
>

## 6. 完稿后必做的校验

写完 Markdown 后，对着原型/PRD 逐项过一遍：

- [ ] 每个出现的【按钮】【菜单】【字段】在原型里都能找到，没有自己编的名字。
- [ ] 每个角色的权限范围和 PRD 里的权限矩阵对得上，没写超权限的操作。
- [ ] 不可逆操作都加了 ⚠️ 警示。
- [ ] 菜单层级和系统实际导航一致，没有跳级。
- [ ] FAQ 里的问题是真问题，不是凑数。
- [ ] 没有"本系统采用先进的 XX 技术"这种营销废话。

发现不一致的地方，单独列一个"待用户确认清单"放在文档最前面，不要偷偷改。

## 7. 导出 Word

Markdown 定稿后，调用 docx skill 导出 `.docx`：

- 封面单独一页，居中。
- 一级标题用政务蓝（#1F3864），加粗。
- 自动生成目录（Word 引用→目录）。
- 表格用三线表。
- 页眉放系统名，页脚放页码。

导出后告诉用户文件路径，并提醒他：截图占位符需要逐个替换为真实截图；版本号和发布日期按实际填。

## 8. 不要做的事

- 不要在没有原型的情况下直接写正文，先列大纲跟用户确认。
- 不要把开发文档（接口、数据库表结构）写进操作手册。
- 不要一章里混写多个角色的操作。
- 不要用 Markdown 表格装超长步骤，步骤就用有序列表。
- 不要自动生成截图，用占位符。
