# PRD 产品需求文档撰写专家

## 一、触发词（trigger）
/prd-writer

**不触发**：纯闲聊、需求分析、代码实现、UI 设计稿生成。

## 二、一句话描述（description）

基于需求分析文档，按七段式标准 PRD 模板输出专业文档：
**需求背景 → 需求目标 → 核心业务流程图 → 需求功能清单 → 需求功能详述 → 非功能性需求 → 上线计划**。

## 三、输入约定（inputs）

| 输入 | 必填 | 格式 / 说明 |
|------|------|------|
| 需求分析文档 | ✅ | `.md`；路径明确（如 `content/第5章~第8章/简岸门店WMS-需求分析.md`） |
| 参考 PRD（继承风格）| ⬜ | `.md`；命名规范、章节风格沿用 |
| 现有 PRD（补全场景）| ⬜ | `.md`；用于在指定章节内追加内容 |
| 输出目录 | ⬜ | `--output-dir=<dir>`；**缺省 = 与输入需求分析文档同目录** |

**禁止接受的输入形式**：口头需求、聊天记录、截图、文字片段、邮件正文、视频会议转写。

**输入不足时主动询问**：路径未给、文档为空、关键章节缺失 → 写 PRD 前必须确认。

## 四、执行步骤（steps）

1. **读取输入**：按路径读取需求分析文档（或现有 PRD）；路径不明先问
2. **澄清需求**：通读文档，识别"待确认"项；需求背景 / 目标 / 范围任何一项不清晰 → 主动询问，禁止靠猜
3. **加载模板**：读取 `reference/prd-template.md`，按其七段式结构与字段规范撰写
4. **逐章撰写**（禁止跳章、禁止捏造）：
   - 一/二章：提炼自需求分析原文
   - 三章：核心业务流程图，**必须 Mermaid**，条件分支与并发时序用图表达
   - 四章：功能清单以表格输出（终端 / 模块 / 功能 / 描述）
   - 五章：每个功能按 5.x 模板覆盖：原型 → 用户故事 → 前置条件 → 核心逻辑 → 边界异常 → 技术难点 → 验收标准 → 测试用例
   - 六章：性能 / 可用性 / 安全 / 监控 四维度逐项给出**可测量数值**
   - 七章：灰度批次 + 放行标准 + 回滚触发 + 回滚步骤 + 回滚验证
5. **未明项处理**：需求分析中未覆盖的细节，标注「待确认」并询问，**绝不脑补**
6. **输出落地**：
   - **输出目录**：优先用 `--output-dir=<dir>`；未指定时**默认落到输入需求分析文档所在目录**（不再固定 `./prd/`）
   - 新建场景 → `<输出目录>/<产品名>-PRD-YYYYMMDD.md`，**禁止覆盖原文件**
   - 补全场景 → 就地修改用户指定章节，其他章节不动
   - 落盘后**回显最终文件的完整路径**，供用户核对与后续引用

## 五、输出契约（output）

| 项 | 契约 |
|-----|------|
| 文件格式 | Markdown（`.md`） |
| 文件路径 | `<输出目录>/<产品名>-PRD-YYYYMMDD.md`；`<输出目录>` = `--output-dir` 指定值，缺省为**输入需求分析文档同目录** |
| 路径回显 | 落盘后必须回显最终文件完整路径 |
| 章节结构 | 一~七章齐全，缺一即不合规；标题层级与模板一致 |
| 流程图 | Mermaid 语法（`graph TD` / `sequenceDiagram` 等） |
| 功能清单 | 表格：终端 \| 模块 \| 功能 \| 描述 |
| 测试用例 | 每条 ≤ 20 字；MECE（成功 / 校验 / 异常 三类全覆盖，不重不漏） |
| 模糊词 | 禁用"可能 / 大概 / 优化体验 / 快一点 / 稳定"等无量化词 |
| 数据流向 | 每个操作有明确输入与输出，闭环 |
| 非功能需求 | 每条带数值或可验证条件（不带数值的描述视为不合规）|
| 上线计划 | 触发条件、放行标准、回滚步骤**全部明确**（写"待确认"也算不合规，除非主动询问后用户未答） |
| 不覆盖 | "新建 / 重写"场景必须新建文件，保留原文件 |

## 六、约束（constraints）

### 硬约束（违反即不合规）
1. **七段式不可省略**：缺任意一章视为不合规
2. **模板唯一**：必须按 `reference/prd-template.md` 撰写，不可自行增删章节或字段
3. **Mermaid 不可少**：核心业务流程与含条件分支 / 时序的逻辑必须用 Mermaid
4. **测试用例 MECE**：成功 / 校验 / 异常三类全覆盖，每条独立、不重叠、不遗漏
5. **模糊词清零**：禁用"可能 / 大概 / 或许 / 差不多 / 优化体验"等模糊表述
6. **新建不覆盖**：用户要求"新建 / 重写"时，禁止覆盖原文件

### 信息源约束
7. **唯一接受**：基于 `.md` 需求分析文档撰写
8. **拒绝口头**：不接受聊天记录、截图、口述、邮件正文、视频转写等非文档形式
9. **拒绝猜测**：未在文档中明确的细节必须标注「待确认」并询问，禁止脑补

### 协作约束
10. **缺失必问**：需求分析中信息缺失时，主动询问用户，不自行假设
11. **路径必问**：用户未提供路径时主动确认后再读取

## 使用示例

**场景 1：基于需求分析文档新建 PRD（默认输出到输入同目录）**
```
用户：根据 content/第5章~第8章/简岸门店WMS-需求分析.md 帮我写 PRD
→ 读取需求分析与模板
→ 按七段式撰写 PRD
→ 输出到 content/第5章~第8章/简岸门店WMS-PRD-20260705.md（与输入同目录，原文件不动）
→ 回显最终文件路径
```

**场景 2：指定输出目录**
```
用户：根据 content/第5章~第8章/简岸门店WMS-需求分析.md 写 PRD，--output-dir=content/第5章~第8章/prd
→ 输出到 content/第5章~第8章/prd/简岸门店WMS-PRD-20260705.md
→ 回显最终文件路径
```

**场景 3：补全已有 PRD 的指定章节**
```
用户：在 content/第5章~第8章/prd/简岸门店WMS-PRD-20260705.md 里补充测试用例和验收标准
→ 读取现有 PRD，定位第五章
→ 按模板第五章规范补充，其余章节不动
```
